About

I build and run the infrastructure behind CoStar Group's commercial real-estate auction platform. That means Kubernetes, AWS, and the delivery pipelines that put code in front of bidders.

Most of what I do is migration work on systems that can't go down. I've moved fifteen services from Java to .NET, replaced the ingress layer across production clusters, and changed how the fleet gets its nodes. Earlier there was a greenfield serverless product I built from an empty AWS account, and before that, the migration that first put this platform on managed Kubernetes at all. Two things matter to me throughout: making a risky change cheap to undo, and proving a fix worked rather than asserting it.

If there's a thread, it's that I try not to solve the same problem twice. A build fix became the document new teams onboarded against. A rollout fix went into the shared chart, so every team inherited it without asking. A migration became versioned modules and a runbook someone else could follow without me.

My doctorate examined how organisations in the US real estate industry adopt AI to improve performance, the same industry I build infrastructure for. It points at what I'd like to build next: platforms that can carry AI and ML workloads without giving up the reliability and cost discipline the rest of the estate runs on.

Microservices Platform Migration: Java to .NET

Infrastructure owner · 2025–2026 · 15 microservices, 4 environments

A live transaction platform was being rewritten from Java to .NET, and I owned every layer of infrastructure underneath it. That meant the pipelines that built and released it, the Kubernetes deployments and mesh routing, the secrets it needed at runtime, and the database changes that had to land alongside the code. I wrote the promotion gates and the rollback playbooks, and built the maintenance window at the Akamai edge that carried the cutover, rehearsing it in test before running it in production on the night.

The first services wouldn't build at all. Once I found why, I turned the fix into a written convention rather than a one-off repair, so every team after us started from a pattern instead of a puzzle. The second wave cost a fraction of the first, and we shipped on schedule.

Secrets and Access Layer for a New Service Fleet

Infrastructure owner · 2025–2026 · 15 services, 4 environments

Every service in the new fleet needed the same handful of things before it could start, and none of them existed yet. I built that layer. Secrets are pulled from a central vault at runtime instead of baked into images, cache and database access is granted through workload IAM roles instead of static passwords, message-bus credentials are issued per service, and schema changes go out through a gated pipeline rather than by hand.

What lasted was taking long-lived static credentials out of the runtime path altogether. Access became role-based and auditable, and standing up a new service turned into a checklist anyone could follow instead of knowledge that lived in my head.

Zero-Downtime Deploys, Fleet-Wide

One fix in the shared chart · 2026 · every consuming team

Rollouts retire old pods on a fixed delay. If that delay is shorter than a service needs to finish what it's holding, requests get cut off mid-flight, and nothing alerts on it, so it carries on unnoticed. I measured how long each service actually took to shut down and set the timing in the shared chart rather than service by service, so every team using that chart got the fix without doing anything. I confirmed it with controlled load testing rather than trusting a quiet alert channel.

Fleet Capacity, Cost & Node Provisioning

Infrastructure lead · 2024–2026 · multiple clusters, 15+ services

I replaced a third-party node provisioner with the CNCF-standard autoscaler, one environment at a time over five months, leaving production to soak before finishing. The reason wasn't cost. It was getting a third-party dependency out of the path every cluster depends on for capacity. I designed the node pools deliberately rather than by default: cheap interruptible capacity for ordinary workloads, reserved capacity held back for the ones that can't tolerate an eviction. Those same clusters were going through managed Kubernetes upgrades at the time, which I ran under change control, including for a product vertical outside my own team.

On the workload side I introduced hybrid autoscaling: schedules handle the load we can predict, metrics catch the load we can't. Off-hours non-production cost fell by roughly two thirds, though I reverted the savings on several business-critical services before merge, once the load analysis showed they needed that headroom for peak events.

Notes

Three things that cost me time, in case they cost someone else less.

Topology-aware routing is not a switch

It needs three ready endpoints in every zone and zone-labelled nodes. Below that, the annotation is accepted and silently does nothing, so check the EndpointSlice rather than your config.

DynamoDB billing mode cannot change on a replicated table

Replicas off, mode changed, replicas back. Because Terraform declares both in one resource, that is three deliberate applies rather than one.

Scheduled and metric autoscaling together: max wins

The highest trigger wins, so a schedule sets the floor and metrics react above it. But min and max always bind, and KEDA quietly reverts hand-edits to the HPA it owns.
